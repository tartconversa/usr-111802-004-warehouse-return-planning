# 仓库补货运营业务数据

来源事件有来源编号、事件编号、修订、外部实体、发生时间和观察时间；同一来源同一事件的更高修订替代先前修订。主体映射只在来源与外部标识的组合内有效，无法映射的事件在现有摘要中列为未归属。通用金额是原始事件上的可选数值，不代表利润、节约额或结算结果。

报告发布接口保留报告正文和摘要哈希，相同编号不接受不同内容。业务口径、结论的适用范围和后续变化的影响需要与原始观察区分。

## 补货建议口径

补货建议按销售消耗与退货回流分阶段核算，区分四类退货数量：

- `return_requested`：已申请退货、货仍在客户侧，尚未产生回流；
- `return_in_transit`：退货已发出、在运回仓库途中；
- 质检结论（inspection 事件，经 `return_ref` 关联退货单 `return_id`，支持分批）：
  `resellable` 计入 `resellable_returns`（可再次销售数量），`unresellable`
  计入 `unresellable_returns`；
- 尚未给出质检结论的部分保留在申请/在途桶中，三部分之和等于退货单原始数量。

只有质检通过、可再次销售的数量允许抵扣需求：净需求 = 销量 − 可再售退货，
建议采购量 = max(0, 净需求 − 可售库存)。申请与在途数量不抵扣（避免采购断货），
但作为预期回流（`pending_returns`）单列并写入建议依据，避免后续重复下单。
找不到退货单的质检单列入 `unlinked_inspections`，只报告不计数；无法映射主体的
事件列入 `unmatched_events`。

每份建议带 `data_version`（对输入清单的 sha256）和 `manifest`（所用每个事件的
来源、编号、修订及所用库存快照），明确它采用了哪一版销售与回流数据。建议通过
`publish_replenishment` 发布后由 DecisionBook 固化：同编号不接受不同内容，一笔
退货状态变化不会悄悄改写已送采购的建议。当前建议可随时按最新质检结果重算；
`review_replenishment_reports` 对照已发布建议的清单与当前数据，输出需要重新审视
的报告、变化原因（事件修订/新增/撤回、库存变化）及各采购行的数量差异，但不修改
任何历史报告。`replenishment(as_of)` 可重建任一时点的历史口径。
